Three ideas that make containers less mysterious

This page is deliberately ordinary HTML and CSS. You can open it in a browser without Docker. Later exercises put the same files behind nginx so you can feel the difference between "content on disk" and "a running container serving that content".

1. Image versus container

An image is a packaged filesystem plus metadata: the bits you build or pull. A container is a running (or stopped) instance of that image. Rebuild the image when the recipe changes; start a new container when you want another copy of the same recipe.

2. Ports are published on purpose

A process listening inside a container is not automatically reachable on your laptop. Publishing a port maps a host address to the container. This lab always binds published ports to 127.0.0.1 so practice traffic stays on your machine.

3. Labels keep cleanup honest

Lab resources carry cloudsprocket.lab=docker. Reset removes only resources with that label, so your other Docker work survives. That rule is not decoration; it is how a practice lab can share your daemon safely.

How to serve this site natively

From the apps/static-site directory, pick one:

python -m http.server 8080 --bind 127.0.0.1

Then open http://127.0.0.1:8080/.

Later, the lab serves the same files with nginx on a reserved lab port. The HTML does not change; the runtime around it does.
